These take an afternoon each and can be done in any order, except that Firebase wants the domain and the signing key before it is finished.

The order that avoids rework

  1. Play Console identity verification — start it now; it is the only thing that can hold up a launch date by weeks.
  2. Buy the domain — everything else references it, and DNS changes need hours to settle.
  3. Create the upload keystore (or turn on Play App Signing) — Firebase needs its SHA-256 fingerprint, so doing this late means redoing the Firebase step.
  4. Firebase project — with the domain and fingerprint in hand it is one sitting.
  5. Email sender — the DNS records go on the domain from step 2.
  6. Hosting — last, because it only needs the domain and serves the verification file that makes the links open in the app.

Never send me these

  • The keystore file or its passwords. Lose control of it and anybody can ship an update as you; lose the file itself and, without Play App Signing, the app can never be updated again. I only need the certificate's SHA-256 fingerprint, which is public by design.
  • API keys or service-account JSON for email or Google Cloud. Those go into Cloud Functions secrets, never into the repository — an email key in git history is a spam relay somebody else owns.
  • Your Google account password, or 2FA codes. Nothing here needs me signed in as you.

What Phase 2 does not need

Worth stating, because most apps at this point collect a drawer full of vendors. The design rules these out rather than leaving them for later.

  • No ad network
  • No analytics or attribution SDK
  • No Google or Apple sign-in — there is no login
  • No maps or geocoding key — the globe is drawn geometry
  • No payment processor
  • No CDN — the banis and audio ship in the app
  • No push vendor — Firebase covers it if we add group push
  • No AI or LLM account — Vichar reads reviewed sources
