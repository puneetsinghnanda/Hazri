## 0. How to use this document (read first, Claude Code)

**Where things are**

- `docs/PRD.md` — this document: scope, roadmap and decisions.
- `docs/features/NN-*.md` — **the behaviour spec, one file per feature** (§3.5). Where a feature file and this document disagree, the feature file wins.
- `design/canvas.html` — every screen on one page, by feature, each marked current, new or superseded (Appendix A.2).

The design package as first delivered:

```
design/
   ├─ screens.json             ← index of every screen: name, title, frame size, designed theme, file stem
   ├─ tokens.json              ← colours (light + dark), fonts, type scale, radii, sizes
   ├─ html/NN-Name.light.html  ← visual spec per screen, light theme (open in a browser)
   ├─ html/NN-Name.dark.html   ← same screen, dark theme
   ├─ html/00-Foundations.html ← design-system sheet (colours, type, components, motif)
   ├─ screens/NN-Name.{light,dark}.png ← 2× renders of each screen
   └─ data/                    ← dev fixtures: sample-japji.json, gurpurab-558.sample.json
```

Live design canvas (all screens by feature, current and superseded): <https://claude.ai/artifact/Fz2WJs5tPF9nUWPgkgBkR8>, published from `design/canvas.html`. The Phase 1 canvas was https://claude.ai/code/artifact/f601efc5-8bb5-4b87-8dfc-fc70dd4f08c5. Phase 2 screens are generated by `tools/design/build_phase2.py`; numbers 62–84 belong to a superseded Phase 3 set and are not reused.

**Rules for implementation**

1. **The HTML files are the visual spec, not code to port.** Frames are 390 × 844 CSS px = 390 × 844 dp. Match layout, spacing, radii, colours and type from the HTML/CSS; build with Flutter widgets. Artboards titled "full scroll" are taller than a phone and show the whole scrolling content.
2. **Behaviour comes from this PRD and the feature files in `docs/features/`.** Where a design and either disagree, the written behaviour wins; where this PRD and a feature file disagree, the feature file wins. Flag the conflict in the PR description. Superseded designs are history, not spec.
3. **Never create, paraphrase, auto-translate or AI-generate Gurbani text, Gurbani audio, meanings or images of the Gurus.** All Gurbani and meanings come only from the content pipeline (§8). Sample text in the designs and `design/data/` is a placeholder. English/Hindi meanings in the designs are placeholder paraphrases.
4. **No ad SDKs, no third-party tracking or attribution SDKs, no login, ever.** Phase 1 goes further: it makes no network requests at all, `INTERNET` is removed from the merged manifest, and ਅੱਜ ਦਾ ਵਿਚਾਰ is bundled rather than fetched, which is what allows that. **Phase 2 restores `INTERNET`** and adds Firebase; what it may then send is the closed list in §13.1. Three things hold across every phase and are not negotiable: **no password and no sign-in screen**; **no request is needed to read a bani, hear it, see the calendar or write the diary**; and **the sangat is opt-in**, so somebody who never joins it is reading, listening and keeping a diary entirely on their own phone.
5. **All UI strings are localised** (Punjabi, Hindi, English) from day one. No hard-coded user-facing strings.
6. **Keep platform-specific code behind interfaces** (§6.4) so a second platform would need new adapters, not rewrites. iOS is off the roadmap; the discipline stays, because it is also what makes the platform bits testable.
7. Work milestone by milestone (§15). Each milestone ends with passing tests, `flutter analyze` clean, and a short changelog.
8. Copy these rules into the repo's `CLAUDE.md` at M0 so they apply to every session.

## 1. Product summary

Hazri is a free, offline-first Nitnem app in Punjabi, Hindi and English. Its
heart is **hazri** — one bani completed, or five minutes of Naam Simran,
marks the day present before Waheguru — kept on the phone, with no sign-in.
Phase 2 adds what the owner specified on 2026-10-07 and 2026-10-08 (§3.5):
daily **goals**, an optional **profile** with a weekly **backup**, the
**Sangat** (groups working toward one shared goal), the **Simran globe**,
and **badges** for days kept (§3.4, 3.2). Phase 1's promise, which still
stands:

- **All seven Nitnem banis, Ardas and Sukhmani Sahib**, with audio, in Gurmukhi, Devanagari and Roman, with simple meanings in three languages.
- **Text follows the paath**: the current line and word are highlighted and the page auto-scrolls with the audio.
- **Paath keeps playing** when the app is minimised or the phone is locked.
- **Reminders at the user's own times** or automatically from local sunrise/sunset.
- A gentle **Nitnem Diary**, **Paath goals**, **Daily Simran (5 min)**, **ਅੱਜ ਦਾ ਵਿਚਾਰ** with a share card, and a **Gurpurab / Nanakshahi calendar**.
- **Works offline · No login · No ads on Gurbani — ever.**

### 1.1 Target users

| Persona | Needs |
|---|---|
| Daily Nitnem keeper (25–60), India & diaspora | Reliable text, audio for commute, reminders, resume where left |
| Hindi-reading Sikh / Sehajdhari families | Correct Devanagari with meanings in Hindi; Hindi UI |
| Learner / diaspora youth | Roman transliteration, English meanings, follow-along audio |
| Elders | Very large text, big buttons, simple screens (Elder mode) |

### 1.2 Principles (non-negotiable)

1. **Respect (maryada) first.** No ads or promotions near Gurbani. No points or XP for Gurbani. No guilt-tripping streak messages. Gurbani in notifications is limited to bani names.
2. **Accuracy.** Only reviewed text and licensed meanings. Every source is credited in About.
3. **Offline by default.** Everything works with no network.
4. **Calm design.** "Amrit Vela" visual language: dawn-mist light, deep-night dark, Neela (navy) + Kesri (saffron), the day-arc motif.
5. **Budget phones matter.** Small download, fast start, smooth scrolling on 3 GB RAM devices.

### 3.4 Phase 3 — in scope (features 3.1–3.7)

**What was removed.** Recitation check, kids' kantth mode and Gurmukhi

**3.1 Report an issue / Feedback.** The app has never had a way for a reader
to say that a line is wrong, and rule 3 is why that is the report that
matters most: no correction can be typed into Dart, so a fix is a change to
`content/source/` and a rebuilt `content.db`. The form should carry what a
correction needs — the bani, the line, what is wrong — and let anything else
be said in the reader's own words.

This is the **one place free text leaves the phone**, and the privacy screen
has to say so. §13's "no free text" is a rule about analytics: it stops the
app reporting what somebody wrote in their diary. A feedback message is the
opposite — it is sent because the reader typed it and pressed send. It must
never travel through Analytics, and it carries no identifier beyond what the
reader chooses to put in it. D10 earmarked this feature; this is it.

**3.2 Badges** (was "Points and badges"). **Specified 2026-10-08 in
`docs/features/12-badges.md`, designs 95–99 chosen the same day.** That file
is the behaviour; this is the summary.

*No points, ever.* D14 is resolved by honouring §1.2 as written — "No points
or XP for Gurbani" — rather than amending it: there is no score, no XP, no
total and no exchange rate between banis. Badges count **days and
milestones** from rows the Diary already holds (`completions` and
`simranSessions`), plus two Sangat facts the server already has. Nothing
counts paath beside the Diary, and the hazri count is recalculated, never
stored; only which badges were earned, and when, is stored (`badges`,
`user.db` schema version 6).

The four constraints that were set before a line was written all hold:
**never a ranking** against anybody; **nothing is ever taken away** — counts
are totals, never runs, so a missed day resets nothing and needs no grace;
**no notification** about badges at all; and **derived, never a second
record of practice**.

*The ten.* A name that Sikhi confers on a person is not an app's to hand
out, so **Khalsa, Sant, Brahmgyani, Granthi and Bhai Sahib are excluded on
purpose**, and so, since 2026-10-08, are **Gyani and Pracharak**, replaced by
Vichari and Satsangi (D11, BD-3).

| 2 | Shardhalu | ਸ਼ਰਧਾਲੂ | Coming back with shardha | Hazri on 7 days |
| 3 | Abhyasi | ਅਭਿਆਸੀ | One who practises | Hazri on 40 days |

**3.3 Sehaj Path and marker.** This is two different features wearing one
name, and which one is meant is a decision, not a detail (D12):

- **The marker only.** The reader is doing a Sehaj Path from a Saroop or at a
  Gurdwara, and the app remembers where they are: an Ang number, a date, how
  far to go. It ships no scripture, needs no licence, and is a small feature.
- **The path in the app.** Reading the Sehaj Path *on the phone* needs the
  full 1430 Angs of Sri Guru Granth Sahib Ji in `content.db` — roughly a
  hundred times the text the app ships today, under a licence that D1 has not
  settled for the nine banis it already has. That is a content programme, not
  a screen, and it should be costed as one before it is promised.

The marker is the one that can be built on the current content; the app must
not imply it holds the full Saroop while it holds nine banis.

**3.4 Rate the app.** Google Play's In-App Review API (`in_app_review`).
Two things to design around rather than discover: Play **rate-limits the
prompt** and gives the app no way to know whether it was shown or what was
chosen, so the flow must never depend on the outcome and must never nag; and
a plain "Rate on Play" row in Settings is needed as well, because the
in-app sheet cannot be relied on to appear when somebody deliberately asks
to leave a review. Never ask on the way out of a failure, never gate anything
behind rating, and never ask a reader who has just used Report an issue.

**3.5 Digital Gurdwara visit.** Asked as a question — *is it possible?* Yes,
and there are three routes, in rising order of what they cost:

1. **Google Street View where it already exists.** Google holds Street View
   and photosphere coverage in and around a number of Gurdwaras, including
   the parikrama at Sri Harmandir Sahib. Embedding it is a Maps API key, a
   billing account and a view; the imagery costs nothing to make. The limit
   is that the coverage is Google's: it is only where they went, and it can
   change without notice.
2. **The app's own 360° tour.** Capture with a 360 camera, host equirectangular
   panoramas, render them in a panorama view with hotspots between them. Full
   control, and it reaches Gurdwaras Google has never been to. It is also the
   **first thing in this app that needs real hosting** — panoramas are large
   and Firebase's free tier will not carry them, which collides with "still
   free, no own server".
3. **A dollhouse scan** (Matterport and its like). The best result, the
   highest cost, a per-space licence and a third-party dependency for
   something the app would then depend on.

What decides this is not the rendering. It is **permission and maryada**:
filming inside a Gurdwara needs the management committee's consent — SGPC for
Sri Harmandir Sahib — and photography is restricted or forbidden inside the
sanctum at many. Rule 3 applies unchanged: no imagery depicting the Gurus,
and what may be shown of Sri Guru Granth Sahib Ji is the committee's answer
to give, not the app's to assume. It is also the first feature that does not
work with the radio off, which §14's offline line has to be amended for.

Recommended shape: start at (1) for the Gurdwaras Google already covers,
which costs a key and proves whether anybody uses it, and commission (2) only
for a specific Gurdwara that has said yes in writing.

**3.6 Analytics collection switched on**, with the opt-out working. Unchanged
from the old 3.17 and specified in §13.1: this is the phase where collection
goes on, Crashlytics is added, the Settings switch becomes live, and the
privacy screen names analytics as a fourth category. The table in §13.1 and
that screen move together or not at all.

**3.7 Notifications, local and pushed.**

*Specified 2026-10-07 in `docs/features/02-notifications.md`*, which is now
the behaviour and the closed list: Amrit Vela at 04:00, a reminder per goal
item at its own time, Gurpurabs at 06:00 and other Sikh events at 07:00 on
the day, a hazri nudge at 07:00 when there is no goal and no hazri yet, and,
by push, the Sangat's 21:00 message, new members for a group's creator, and
a group ending (summary in §3.5). Everything below this paragraph is the
analysis of 2026-09-26 that led there; where it differs from the file — the
Rehras, Kirtan Sohila and Daily Simran reminders, the evening-before
Gurpurab message, the daily cap of two — the file wins.

*What already exists, and needs no Firebase.* Five reminder kinds are built
and shipping: `amritVela`, `evening`, `bedtime`, `simran` and `gurpurab`,
across four channels (Nitnem reminders, Daily Simran, Gurpurab, Paath goals),
scheduled on the phone by `flutter_local_notifications` on a rolling 7-day
window capped at 60 pending (§1.10). Items 1, 2 and 3 of the owner's list are
therefore **already in the app**; what they need is finishing, not inventing.

*The one distinction that decides the whole feature.* A notification is
**local** if the phone already knows everything needed to decide when it
fires, and **pushed** if the reason for it happened somewhere else. Only two
of the eight asked for are genuinely pushed. That matters because rule 4 says
the sangat is opt-in: somebody who never joins has no account, no token, and
can receive no push at all — so every notification that must reach *everyone*
has to be local, by construction.

| # | Notification | Local or push | State |
|---|---|---|---|
| 1 | Daily morning reminder | local | **built** (`amritVela`) |
| 2 | One per goal | local | **specified** per goal item (`04-goals.md` RM1–RM6); the code once planned none |
| 3 | Gurpurab | local | **built**, and was wrong until 2026-09-23. **Specified 2026-10-07:** 06:00 on the day, not the evening before |
| 4 | Sikhi event | local | **specified:** 07:00 on the day, from the 147 events in `calendar_event` |
| 5 | You were added to a sangat | **push** | **removed** from the list on 2026-10-07 (N-2, open); the creator's *new members* message is in it |
| 6 | The day's sangat goal, consolidated | **push** | **specified:** 21:00 in each member's time, by a Cloud Function (`02-notifications.md` §8) |
| 7 | Your goals for the day are done | local | **an in-app sheet**, once a day (`04-goals.md` CE1, design 61), not a notification |
| 8 | A badge earned | local | **decided 2026-10-08: an in-app bottom sheet** (design 95), never a system notification (`12-badges.md` AN1–AN4, BD-11) |

*7 is the one to reconsider.* The person is holding the phone at the moment
their last goal completes — they tapped the thing that completed it. A
notification tells them what the screen in their hand already says. Ship it
as the in-app moment it is, and if it stays a notification, make it **off by
default** and fire it only when the completion arrived from another device
through sync.

*What is missing from the list.* Ordered by what they cost:

- **Sangrand** — the Nanakshahi month turning. Twelve of them a year, already
  in `calendar_event`, and the one date in the year a Nanakshahi app should
  not be silent about. Local.
- **Somebody joined your group** — the mirror of 5, for the admin who sent
  the invite and cannot otherwise tell. Push.
- **A group goal is nearly over, and a group goal is reached** — `endsAt`
  exists on the goal and nothing looks at it. Two notifications, both push,
  and the second is the only genuinely happy one in the list.
- **A paath logged toward a group goal.** Tempting and wrong as its own
  notification: in a family of six it is six a day. **It belongs inside 6's
  daily digest**, and that is the reason 6 is a digest.
- **A new Vichar entry published** — the library is empty today and nothing
  will tell anybody when it stops being empty. Push, and the only marketing-
  shaped notification here, so it is off unless asked for.
- **"The line you reported has been corrected"** — closes the loop on 3.1.
  Rare, entirely welcome, and the reason somebody reports a second error.
  Push, to the reporter alone.
- **You left a bani part-read** — "Japji Sahib, you stopped at pauri 21",
  later the same day, once. Local, and the most likely of these to be
  genuinely useful.
- **The Sehaj Path marker has not moved in a week** (3.3, if D12 picks the
  marker). Local, gentle, and off by default.

*Rules that bind every one of them.* These are not preferences:

- **§0 stands: "Gurbani in notifications is limited to bani names."** No line
  of Gurbani in a notification body, no ਅੱਜ ਦਾ ਵਿਚਾਰ in a push. The Vichar is
  read in the app.
- **No streak notifications** (§12, unchanged) and no notification that
  somebody missed, lost or is behind. Nothing is ever framed as a loss.
- **Nothing names another person's shortfall.** A digest says what the group
  did together; it never reports that one member did nothing. A family group
  makes this a household matter, not a product decision.
- **Silence windows:** nothing at night beyond the reminders the person set
  themselves, nothing while a simran sitting is running, nothing while the
  reader is open.
- **A daily cap** on everything except the reminders the person configured.
  Two is a reasonable starting number.
- **Every category has its own switch**, and every pushed category is off
  until somebody joins the sangat, because until then there is nobody to
  push to.

*What sends a push.* FCM does not send by itself, some server has to call it,
and **that is now a Cloud Function.** The project moved to Blaze on
2026-09-26 with a ₹2,000/month spend cap, which closes D13. The alternative
considered — a scheduled Vercel job holding a service-account key — is
dropped, and with it the only thing in this project that would have needed a
**secret held off the phone**. A Function runs with the project's own
credentials and there is no service-account JSON to keep anywhere.

`docs/features/00-platform.md` holds the Functions contract that every one of
these obeys: `maxInstances: 10`, `minInstances: 0`, never write to your own
trigger, idempotent always, and an emulator test that includes running it
twice. Those matter more than the spend cap, because costs record up to
24 hours late and a cap therefore lags a runaway by a day.

*Tokens are personal data, and the privacy screen has to say so.* An FCM
registration token identifies a device. It is written to the user's own
document, it is rotated by the SDK, it must be **deleted when the account is
deleted** — the "Delete my account and data" button already exists and must
take the token with it — and it must be removed, not merely ignored, when
somebody turns every pushed category off. §13.1 carries the row.

*A gap worth knowing before item 4 is built.* Of the 147 calendar events,

  so many paath of one bani, or so many Naam Simran sittings of at least M
  minutes, ending within 365 days.
- **Three built-in groups** — Amrit Vela Sangat, Simran Sangat, Sukhmani
  Sahib Sangat — configured in the admin website. Anybody can join or leave,
  with or without a profile; the goal resets when it is met or runs out.

  is sent from an outbox when the phone is back online.

  the second appears only on a day that had a goal (green when met, grey
  when not). Green never appears without orange. No red, no crosses.
- The day screen (design 56) lists every paath with its count, times and
  source, and **+ and −** for each bani and Naam Simran, for today and the
  7 days before it.
- **The streak card** (design 87): *days in a row now* and *your longest*,
  from one function `nitnemStreak`, which Today's card also calls. Grace days
  are granted silently, two a month, and never mentioned.
- No diary sync switch and no per-day sync: the weekly backup replaces it.
- Open: Y-3 (export).

#### Weekly backup and restore (`10-backup.md`)

- **Only with a profile.** Every Sunday at 00:00 local time (plus up to an
  hour of jitter), and by hand with **Back up now**, the app sends every
  goal, goal item, completion, simran sitting and earned badge changed since
  the last backup. Any network.
- **Restore my data**, on the profile screen after a profile restore, merges
  row by row: it adds what the phone lacks, keeps the newer of two versions,
  and never deletes or touches what it did not receive. With two active
  goals the phone's stays active.
- The restore screen says the copy is as of the last backup and that
  anything after it is not included. Backups are kept while the profile
  exists.
- Not backed up: reminders, settings, grace days, the profile itself and the
  Sangat (the server already holds them).

#### Admin website (`11-admin.md`)

- A separate Firebase Hosting site, `hazri-admin.web.app`, linked from
  nowhere. **Google sign-in, on the website only**, accepted for the one
  admin email; the server checks it on every request (`403 NOT_ADMIN`).
- Runs the built-in Sangat groups, acts on reported groups, raises a
  person's custom-group limit, and shows counts from Hazri's own Firestore
  data. No third-party analytics. Every change is written to an audit log.
- The app still has no sign-in screen; this does not change rule 4.

### 7.3 Timing file format (per audio track)

```json
{
  "track": "japji_sgpc_voice1", "durationMs": 1144000, "version": 3,
  "lines": [
    { "line": 0, "s": 1200, "e": 9800,
      "w": [[1200,1900],[1900,2600],[2600,3400]] }
  ]
}
```

`line` = `line.idx`; `w` = word start/end ms in Gurmukhi word order. Words may be omitted for a line (line-level highlight only). Lines not recited (e.g. headings) are absent.

## 8. Content and asset pipeline (`tools/content_pipeline`)

A repeatable script (Dart or Python) that builds `assets/content/content.db`. **Nothing Gurbani-related is typed by hand in app code.**

| Content | Source (to confirm — see §18) | Pipeline rules |
|---|---|---|
| Gurbani text (Gurmukhi Unicode), Devanagari, Roman | BaniDB (Khalis Foundation) banis data, subject to licence approval; alternative: another openly licensed Gurbani database | Store Unicode, not legacy ASCII fonts. Validate that Devanagari and Roman word counts equal Gurmukhi word counts per line; if not, mark the line `word_align=false` (line-only highlight) and list it in a report for scholar review |

| Meanings pa / hi / en | Licensed teeka/translations (e.g., Prof. Sahib Singh for Punjabi; an approved Hindi teeka; an approved English translation) | Store `source_id` for credits. No machine translation |
| Bani versions | SGPC Rehat Maryada versions (default) | Phase 1 ships SGPC only unless alternate text **and** audio exist |
| Audio | Commissioned recordings with written rights assignment (one paathi, SGPC versions) | Mono AAC (.m4a) 64 kbps, loudness-normalised (−16 LUFS), no music. Until final audio exists, use clearly labelled dev placeholders |
| Timings | Forced alignment of final audio against the text, then human verification in `tools/timing_tool` | Line timings must be verified by a human. Word timings: aligner output, fallback = split line duration by syllable weight |
| Gurpurab & Nanakshahi | Official SGPC calendar (jantri) for the NS year | Bundle current + next NS year when available; update yearly via app update |
| Cities | Open city dataset (e.g., GeoNames cities with population > 15 000, CC-BY — credit it) | Names in en; pa/hi names for top Indian + diaspora cities |

### 1.6 Follow audio — Design 13, 15

**Highlight:** past lines muted (`muted` colour); **current line** on `hl` background with 12 dp radius; **current word** in `word` colour with a 2 dp underline; future lines normal. Update on every position tick (target ≤100 ms latency; interpolate between ticks using `DateTime.now()` and speed).

**Auto-scroll:** when the current line changes, animate (250 ms, easeOut) so it sits at ~30 % from the top (`alignment: 0.3`). Don't scroll if the line is already fully visible between 15 % and 60 % of the viewport.

Tap pill → re-attach and scroll to the current line.

**Tap a line to jump:** tap on any line seeks audio to that line's start (`s`) and re-attaches. Playback state (playing/paused) is unchanged.

**No audio:** follow features are hidden; the reader works as a normal scroller.

### 1.11 ਅੱਜ ਦਾ ਵਿਚਾਰ — Today's Vichar

Replaces the daily Hukamnama. The Hukamnama is issued fresh each morning at Sri
Darbar Sahib and cannot be known offline, so it needs a network provider and a
terms agreement (was §18 D4). ਅੱਜ ਦਾ ਵਿਚਾਰ needs neither: one line of Gurbani a
day, bundled, working in airplane mode like the rest of the app.

- **Content:** 200 reviewed lines from Sri Guru Granth Sahib Ji, each with a
  Punjabi meaning and an English meaning, in
  `content/source/vichar/gurbani-200.json` → the `vichar` table in content.db.
  Nothing is written by the app (§0.3).
- **Which line:** round robin on the date itself — days since the epoch, modulo
  the collection size. Everyone opening the app on a given day sees the same
  line; a phone that was off for a week has no backlog; reinstalling changes
  nothing. After 200 days it begins again.
- **Attribution:** "Sri Guru Granth Sahib Ji". This dataset carries no Ang
  numbers and the app does not invent one. If Angs are supplied later the card
  gains "Ang N · Sri Guru Granth Sahib Ji".
- **Languages:** Punjabi and English meanings ship. Hindi falls back to the
  Punjabi meaning — closer for that reader than English — until a reviewed
  Hindi rendering exists.
- **Today card (full width):** title, source, the line in Gurmukhi, the meaning
  in the UI language, and two actions — **Explore** (opens the screen) and
  **Share**.
- **Screen (`/vichar`):** the line, then its meaning in Punjabi and in English
  as separate cards, then **Share**.

## 10. Design system implementation

### 13.1 What each phase actually sends

The event list above is the design. When it starts running is a separate
decision, taken deliberately, because "we added the SDK" and "we are
collecting" are not the same sentence and a privacy screen that blurs them is
a lie to the reader.

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| `INTERNET` in the merged manifest | removed | **restored** | present |
| Firebase SDKs in the build | none | Core, Auth, **Analytics**, **Messaging** (Sangat pushes only, `02-notifications.md` §8). No client Firestore: every read and write goes through the `api` Cloud Function | the same, plus Crashlytics |
| Analytics collection | n/a | **off** — `setAnalyticsCollectionEnabled(false)` at start-up, before any event can be recorded | **on**, defaulting to on, with the opt-out working |
| Crashlytics | n/a | not added | on, same opt-out |
| Events leaving the phone | none at all | none from Analytics. Otherwise only what a feature file names: the anonymous sign-in; **a profile the person chooses to make** — name, email, city, phone if given — with its verification and restore mail (`01-accounts.md`); with a profile, **the daily attendance mark** (`07-simran.md`) and **the weekly backup** of goals, diary entries and earned badges (`10-backup.md`); for a Sangat member, their paath toward their groups (`08-sangat.md`) | the Phase 2 list, plus the §13 event list, no PII, no free text |
| The Settings opt-out switch | absent | present but inert, and shown as unavailable rather than pretending to work | live, and stops both Analytics and Crashlytics |
| A push token | n/a | **an FCM registration token per device**, only with a profile **and** at least one group; removed when either goes or Sangat notifications are switched off (`02-notifications.md` FT1) | the same |
| Advertising ID | absent | absent | absent |

**"No free text" is a rule about analytics, not about the reader.** Phase 3's
Report an issue (§3.1) sends what somebody typed because they typed it and
pressed send. It does not travel through Analytics and it is not in the event
list above; the row in this table is unchanged by it. The privacy screen has
to name it as its own thing, in the reader's words: a message you chose to
send us.

**Phase 2 ships the Analytics SDK and sends nothing through it.** Wiring it in
Phase 2 means the events are defined, the calls sit where they belong and the
switch already exists; flipping collection on in Phase 3 is then one line and
a truthful privacy screen, rather than a new dependency added late.

**What the privacy screen must say, per phase.** It is the reader's copy of
this table and it is not allowed to run ahead of it. In Phase 1 it says the
app makes no network requests at all. In Phase 2 that sentence is retired:
what it says instead is that nothing is sent unless you make a profile or join
the sangat, that analytics are not being collected, and what each of those
does send — including that the globe shows a profile's city and never a name
(`07-simran.md` PV3). The Phase 2 column above was brought up to the feature
files on 2026-10-08; **the privacy screen is rewritten in the same change that
ships the profile, attendance and the backup**, not after (`01-accounts.md`
§13.4). In Phase 3 it
names analytics as a fourth category and points at the switch.

**Non-functional**

| Area | Requirement |
|---|---|
| Size | Base AAB download ≤ 25 MB; audio in packs only |
| Start-up | Cold start to interactive Today ≤ 1.5 s on a mid-range 2022 phone; ≤ 3 s on a 3 GB RAM budget phone |
| Smoothness | Reader scroll and highlight at 60 fps (no jank > 16 ms in profile mode for a 10-minute run) |
| Sync accuracy | Highlight within 100 ms (target) / 150 ms (max) of timing data |
| Battery | Position ticks only while reader/player UI is visible; background playback uses the media session only |
| Offline | Everything except pack downloads works in airplane mode |
| Reliability | Crash-free users ≥ 99.5 %; DB migrations tested |
| Security | No secrets in the repo; Firebase config via `google-services.json` (not committed for release builds if the repo is public) |
